- New frame-related Vrui state:
  - Threads::RunLoop - provides Vrui frame timing via lastDispatchTime
    - Replace Misc::Timer appTime
  - All Vrui time calculations based on Realtime::TimePointMonotonic and Realtime::TimeVector
    - Times still reported to client code as double seconds since the first frame
  - Frame rate cap via minimumFrameTime is enforced at the very beginning of a new frame
  - lastFrame is the application time at the beginning of the current frame
    - Usually a timer snapshot, but can get adjusted when running synchronized
    - Gets reported as Vrui::getApplicationTime
    - Guaranteed 0.0 during first frame
  - lastFrameDelta is difference between lastFrame and previous lastFrame, i.e., exact duration of previous frame
  - animationFrameTime is same as before, using double because exposed to clients
  - nextFrameTime treated as before, using double because exposed to clients
    - Initialize to lastFrame if running continuously, otherwise to infinity
    - Adjust as Vrui::scheduleFrame is called
    - Limit maximum wait time in Threads::RunLoop::waitForEvents
      - Need maximum wait parameter for waitForEvents, specified as time point
  - Do we really need the whole frame time averaging thing? Who uses it?
    - It's used by fps display in windows, but is it needed?
  - Ditch frame rate cap; it's from a time before there was Vrui::scheduleFrame and animation had to run with requestUpdate
  - synchFrameTime/synchWait is used for playing back recordings at real speed
    - Still need it

- New frame sequence:

- A new Vrui frame starts when RunLoop::waitForEvents returns

1. Calculate the time point at which waitForEvents must return
  - If there are unhandled events in any of the X11 event queues, don't wait at all -- this sucks, but is unavoidable, should be checked per-connection after rendering is complete
  - nextFrameTime, result of clients calling Vrui::scheduleFrame or running in continuous mode
  - synchFrameTime, set during previous frame by playback input device adapter

2. Call RunLoop::waitForEvents with a latest wake-up time point

3. If running in synch mode, set time snapshot to synchFrameTime
  - If synch is forced, actually wait
  - How does this play with timers?
    - It doesn't. Timers are based on wall-clock time, not synch-adjusted time. How fix?

4. Start a new Vrui frame
  - Send currentTime to slaves in cluster mode
  - Reset nextFrameTime
    - Set to currentFrameTime if running continuously, otherwise to infinity

5. Call RunLoop::dispatchPendingEvents
  - May update states of physical input devices (Mouse/keyboard/multitouch via X11, HID via I/O watchers, some InputDeviceAdapters can use this)

6. Update the rest of physical input devices
  - Forward device states to slaves in cluster mode

7. Update the input graph

8. Do the rest of frame processing

9. Do rendering
  - Collect a union of "dirty" flags for all X11 event queues used by window groups; rendering calls may pull events from the socket into the queue

10. Repeat from 1.
